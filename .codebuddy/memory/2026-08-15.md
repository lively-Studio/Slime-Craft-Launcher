## 修复 Linux deb 打包的跨架构依赖 bug（方案 A）
- 现象：aarch64 的 .deb 在 ARM 主机 `apt install` 报 "depends libc6:amd64 无法安装"。根因是 jpackage(JDK 17) 在交叉 aarch64 构建时把 control 的 Depends 写成 `libc6:amd64`（带 amd64 后缀），ARM 上只有 `libc6:arm64`。
- 方案 A（用户选定）：覆盖 control 的 Depends 为架构无关。由于 JDK 17 不支持 `--deb-customize`（JDK 18+ 才有），改为**打包后解包 deb → sed 改写 DEBIAN/control 的 Depends 去掉 `:<arch>` 后缀 → dpkg-deb -b --root-owner-group 重新打包**。
- 改动文件：`.github/workflows/linux-pkg.yml`，在 "Build DEB with jpackage" 步骤后新增 "Fix DEB control dependencies" 步骤（x86_64 也会执行但 sed 无匹配则不变，安全）。
- 临时绕过（VM 直接装）：`sudo apt-get install -y --ignore-depends=libc6:amd64 <deb>` 或 `sudo dpkg -i --force-depends <deb>`。
- 顺带为 RPM 加了**检查**步骤（非重打包）：RPM 依赖由 autoReq 按包自身架构生成，aarch64 不会硬编码 amd64，故只做 `rpm -qp --requires` 检查并在发现 x86-64/amd64 误标时 `exit 1`。RPM 无 deb 那种 clean 重打包工具链，因此采用检查+失败策略。改动同在 `linux-pkg.yml`（RPM 步骤后新增 "Inspect RPM requirements"）。

## 更新系统：SNAPSHOT 版本排序 bug 修复
- 现象：用户报告"更新系统认为 SNAPSHOT11 比 SNAPSHOT9 版本低"。
- 根因（经独立复现 VersionNumber 算法验证）：`VersionNumber` 本身对 `DEV2026.1.0-SNAPSHOT-N` 的比较是**正确的**（build 号被解析成数值，11>9）。真正 bug 在 `UpdateChecker.checkUpdate()`：它用 `.findFirst()` 直接返回 GitHub Releases API 创建时间倒序的**第一个**匹配 release，没有按版本号排序。当 `SNAPSHOT-9` 比 `SNAPSHOT-11` 晚创建时，`SNAPSHOT-9` 被当成"最新"，`SNAPSHOT-11` 反被视为更旧。
- 修复：`SCL/src/main/java/studio/lively/scl/upgrade/UpdateChecker.java` 的 `checkUpdate()` 改为收集所有匹配候选，按 `VersionNumber.compare` 取**版本号最大**的 DEV / STABLE 分别作为 `bestDev` / `bestStable`，最后按 channel 返回（NIGHTLY→bestDev??bestStable；DEVELOPMENT→bestDev；STABLE→bestStable）。
- 附带发现（经核实**不存在**，已撤销）：曾误判 `linux-pkg.yml`/`macos-dmg.yml`/`windows-exe.yml` 没传 `SCL_VERSION`。实际这四个 workflow（含 `gradle.yml`）**全部**在 workflow 级设了 `SCL_VERSION: DEV2026.1.0-SNAPSHOT-11`（gradle.yml:17 / linux-pkg.yml:19 / macos-dmg.yml:20 / windows-exe.yml:20），`build.gradle.kts` 读它作为 `version` 写入 manifest，故所有 CI 构建产物的 `scl.version` 都是 `DEV...-SNAPSHOT-N` 格式，版本方案一致，**无需改动任何 workflow**。
- 最终验证（2026-08-16）：直接用仓库真实 `VersionNumber.java` 编译运行，`compare("DEV2026.1.0-SNAPSHOT-11","DEV2026.1.0-SNAPSHOT-9")=+1`（11>9，正确），连无 `-` 的 `SNAPSHOT11` vs `SNAPSHOT9` 也是 +1。证明 `VersionNumber` 比较逻辑无误，**唯一真因就是 `checkUpdate()` 的 `findFirst()` 创建序选取**，已修复。
- 源码 `CurseForgeRemoteAddonRepository.java` 无需改动（本就不含密钥）。若新增 CI 构建 workflow，须同样引用 `secrets.CURSEFORGE_API_KEY`。
